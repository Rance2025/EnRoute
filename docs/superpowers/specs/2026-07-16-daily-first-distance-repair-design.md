# 每日首点距离补全设计

## 背景与目标

外部足迹 App 在跨日或重新开始记录时，会把当天第一条记录的 `distance` 写成 `0`。该字段在 EnRoute 中表示从上一条时间记录移动到当前记录的距离；当前 CSV 导入器原样保存它，导致距离趋势、区域移动距离和相关汇总少计跨日移动。

本次修复包含两个顺序明确的阶段：

1. 先修复增量导入路径，使以后导入的每日首个零距离点自动得到相邻坐标直线距离。
2. 代码验证通过后，先备份并校验备份，再原地修复根目录 `data/footprints.sqlite` 中已有的事实记录和依赖距离的摘要数据。

外部原始文件 `external/backUpData-all.csv` 保持不变。它是第三方导出的原始证据，距离纠正规则属于 EnRoute 的导入规范化职责。

## 已验证的数据事实

当前 CSV 与根目录 SQLite 都包含 40,441 条足迹。134 条记录的 `distance` 为零，并且全部是上海时区某一天的第一条有效记录。除整个数据集的第一条记录外，有 133 条记录存在全局上一点：

- 125 条将补成正距离。
- 8 条因前后坐标相同，补算结果仍为零。
- 补算总距离约为 178,043.732 米。
- 最大两段约为 101,502.721 米和 69,839.799 米；不因定位精度低、速度未知或跨日间隔而舍弃。

现有非零 `distance` 与相邻经纬度的 Haversine 距离高度一致，证明该字段是当前点相对上一点的移动距离，而不是累计里程。

## 距离规范化规则

新增一个独立、可测试的距离规范化单元，由增量导入和现有数据修复共同复用。输入为上一条按时间排序的有效足迹和当前足迹，输出为当前足迹应保存的距离。

仅当以下条件全部满足时补算：

- 当前记录的源 `distance` 精确等于 `0`。
- 存在时间戳严格更早的上一条有效足迹。
- 当前记录与上一条记录在 `Asia/Shanghai` 时区属于不同自然日。

补算使用两点 WGS-84 经纬度的 Haversine 大圆距离，地球平均半径取 6,371,008.8 米。其他情况均保留源值：

- 整个数据集首条没有上一点，保持零。
- 同一天内的零距离不解释为外部 App 断点，保持零。
- 坐标相同会自然得到零。
- 已有正距离原样保留，不重新计算。

不设置时间间隔、距离、accuracy 或 speed 阈值。这里修复的是外部 App 已知的归零行为，不推断交通方式，也不尝试把直线距离还原成真实道路里程。

## 增量导入数据流

`FootprintStore` 在把每条 CSV 足迹写入 `footprints` 之前执行规范化：

1. 按当前记录时间戳从 `footprints` 查询最近的更早记录。
2. 对当前源记录应用每日首点规范化规则。
3. 使用规范化后的记录执行现有 `INSERT OR IGNORE`、空间索引写入、行政区匹配和摘要失效逻辑。
4. 遇到同时间戳既有记录时，也用规范化后的值执行冲突校验，从而允许未经修改的原始 CSV 与已修复数据库保持一致。

导入文件必须按时间戳严格递增。若有效记录倒序或重复时间戳携带冲突内容，导入事务失败并保持原数据库不变。查询数据库前驱而不是只记住 CSV 上一行，确保仅包含新记录的增量文件也能跨批次补算当天首点。

导入规范版本进入导入兼容性签名。规则变更后，已有数据库不会因旧签名而跳过检查；重新扫描原始 CSV 时，规范化结果应与已修复事实层一致。

## 现有事实数据原地修复

新增显式维护命令，默认目标为根目录 `data/footprints.sqlite`。该命令不修改 CSV，也不创建第二份替代数据库。执行顺序如下：

1. 确认 EnRoute API 未持有数据库写入生命周期；若服务正在运行则先停止服务。
2. 在 `data/` 下创建带时间戳的 SQLite 备份文件。
3. 以只读方式打开备份，执行 `PRAGMA integrity_check`，并核对 `footprints`、`footprint_spatial`、`visual_tiles`、`admin_region_daily_stats` 的行数与原库一致。
4. 在原库单一事务中重新扫描按时间排序的 `footprints`，只更新满足规范化条件且计算结果不同的 `distance`。
5. 重建 `admin_regions` 上的 `stay_duration_seconds` 与 `travel_distance_meters` 汇总。
6. 重建 `admin_region_daily_stats`，并更新其来源签名。
7. 提交前验证候选集合、更新数量、距离总和、非负有限值、事实层与空间索引行数，以及派生距离总和。
8. 任一检查失败则回滚事务，保留原库与备份供检查。

维护命令应支持 `--database`，以便测试和在 worktree 数据副本上演练；实际持久数据修复只对根目录数据库执行一次。旧 worktree 内的 SQLite 副本不是持久事实源，不批量修改。

## SQLite 写入边界

允许写入的对象只有：

- `footprints.distance`：只更新已识别的每日首个零距离事实行。
- `admin_regions`：重建已有聚合字段。
- `admin_region_daily_stats`：原子替换距离相关每日摘要。
- `footprint_meta`：更新导入与每日摘要签名。

明确禁止：

- 不删除、重建或标记 `visual_tiles` 为 dirty。
- 不写 `footprint_spatial`，因为坐标没有变化。
- 不删除或重建 `footprints` 表。
- 不调用 `build_visual_tiles` 或 `npm run prepare:footprint-tiles`。
- 不执行无范围的 `DELETE FROM visual_tiles`。

`visual_tiles` 的内容只依赖时间和坐标表示，本次距离字段修复不会改变地图视觉等价结果。

## 错误处理与幂等性

维护命令在以下情况拒绝写入：数据库不存在、必需表缺失、完整性检查失败、时间戳不严格递增、距离或坐标不是有限值、候选记录不符合每日首点规则、备份无法验证，或派生摘要重建失败。

命令是幂等的。第一次执行后，125 条记录由零变为正值；8 条同坐标记录和全局首条仍为零。再次执行应报告零条更新，不改变任何表或签名。

数据库备份不提交 Git，保存在已忽略的 `data/` 目录。执行结果打印备份路径、扫描数、候选数、实际更新数、补入总距离和各相关表的前后行数，但不输出原始敏感坐标列表。

## 测试与验证

测试遵循 TDD，先观察失败再实现。覆盖范围包括：

- 空数据库首条零距离保持不变。
- 同日零距离保持不变。
- 跨上海自然日的零距离按 Haversine 补算。
- 增量文件第一条能使用数据库中的上一点。
- 坐标相同仍为零。
- 大距离、低 accuracy、`speed=-1` 仍补算。
- 正距离原样保留。
- 同时间戳校验使用规范化结果。
- 修复命令只更新目标事实行且可重复执行。
- 备份失败或摘要失败时原库不变。
- `footprints`、`footprint_spatial` 和 `visual_tiles` 行数不变，`visual_tiles` 内容摘要不变。
- `admin_regions` 与 `admin_region_daily_stats` 的距离总和包含补入距离。

实现后运行针对性后端与仓库测试，并执行 `npm test`、`npm run lint`、`npm run build`。当前基线存在一个与本任务无关且可稳定复现的前端失败：`AccountingPage.integration.test.tsx` 的“空当前月自动请求最近导入月”断言；验证报告必须将它与本次距离测试结果分开说明。

实际数据修复前先在 worktree 的数据库副本演练完整流程。根目录原库修复后，再以只读方式核对：40,441 条足迹和空间索引仍完整，`visual_tiles` 仍为 63,221 行且内容摘要未变化，剩余零距离仅包括全局首条及坐标未变化的每日首点，距离查询与区域摘要返回修复后的总量。

## 文档影响

README 的数据口径说明需要补充：导入阶段会纠正外部 App 每日首点归零，`distance` 表示上一足迹到当前足迹的 WGS-84 直线距离；未来自有手机 App 能直接记录连续定位距离后，再替换这一兼容规则。
